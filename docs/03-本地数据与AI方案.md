# HomeMedicineBox MVP 本地数据与 AI 方案文档

## 1. 文档目标

本文档用于指导首版技术方案设计，重点回答以下问题：

- 数据如何只保存在本地。
- 拍照识别如何与本地存储配合。
- 为什么需要“识别草稿”和“正式记录”分层。
- 研发可以如何拆分模块与边界。

平台前提：

- 产品目标平台为 iPhone 和 Android。
- 当前版本技术方案以 `iPhone 优先` 设计与评审，领域模型、草稿流转和提醒规则必须从一开始保持双端可复用。
- 产品长期规划支持多设备同步，但 `v1 不引入账号体系和数据同步链路`。

## 2. 设计原则

- `本地优先`：正式数据、图片和提醒计算都基于本地存储完成。
- `草稿分层`：AI 输出先进入草稿，不直接写入正式业务表。
- `最小上传`：只有用户主动拍摄并触发识别的图片才会发送给第三方 AI。
- `可回退`：AI 不可用时仍能手动完成录入。
- `可追溯`：正式记录应保留原图引用，便于后续核对。
- `同步预留`：实体主键、时间字段和仓储边界需保持可扩展，便于后续接入多设备同步。

## 3. 总体架构

建议以 `本地数据库 + 本地文件存储` 作为双端统一架构原则：

- 结构化数据：存储在本地数据库中。
- 原始图片：存储在 App 沙盒目录中。
- 提醒计算：由本地提醒引擎根据数据库字段计算。
- AI 识别：由客户端发起请求，服务返回结构化草稿结果。

当前版本建议：

- iPhone：采用 `SwiftData 或 Core Data + 本地文件存储`。
- Android：后续版本沿用相同实体模型与状态机，可映射到 `Room/SQLite + 应用私有文件存储`。
- v1：不引入同步服务、账号系统、设备绑定与冲突解决逻辑。

逻辑模块建议如下：

| 模块 | 责任 |
| --- | --- |
| `SecurityGate` | 生物识别 / 设备凭证校验、解锁态管理 |
| `CaptureCoordinator` | 拍照、图片压缩、图片本地暂存、触发识别 |
| `RecognitionService` | 调用第三方 AI 服务，返回结构化草稿 |
| `DraftManager` | 保存、更新、删除识别草稿 |
| `LocalRepository` | 读写成员、药品、就诊事件、文档、批次 |
| `ReminderEngine` | 计算过期和库存提醒，生成本地展示与通知 |
| `ImageStore` | 管理图片落盘、读取、删除 |

### 4.3 面向后续同步的最小预留

- 所有核心实体继续使用 `UUID` 作为全局唯一主键，避免后续多设备合并时重编号。
- 保留 `createdAt` 和 `updatedAt` 作为基础变更时间字段，为未来同步排序和冲突处理提供基础。
- 业务层通过 `LocalRepository` 访问数据，避免页面直接耦合底层数据库实现，后续可在仓储层挂接同步引擎。
- v1 不新增同步状态字段、不实现冲突处理策略，避免为首版引入不必要复杂度。

## 5. 草稿与正式记录分层方案

### 5.1 为什么必须分层

- 医院单据和药盒图片存在模糊、遮挡、反光等问题，AI 识别准确率不可能 100%。
- 如果识别结果直接写入正式记录，会污染提醒、列表和历史查询。
- 用户对健康资料的容错率很低，必须保留“核对后入库”的产品承诺。

### 5.2 状态流转

```text
拍照完成
  -> 创建 RecognitionDraft
  -> 调用 AI 识别
  -> 草稿状态更新为:
     - 待确认
     - 待补充
     - 识别失败
  -> 用户确认保存
  -> 写入正式记录
  -> 草稿标记为已转正
```

### 5.3 转正规则

- `medicine` 草稿确认后，创建 `MedicineItem` 与至少一个 `MedicineBatch`。
- `medical_document` 草稿确认后，创建或追加到 `VisitRecord` 与 `MedicalDocumentRecord`。
- 只有正式记录参与首页展示、提醒计算、搜索结果。

## 6. 图片处理与存储策略

### 6.1 图片生命周期

1. 用户拍照后，图片先写入沙盒临时目录。
2. 客户端对图片进行本地压缩、方向校正、必要的裁剪。
3. 识别完成后，图片移动到正式本地目录并生成 `LocalImageAsset`。
4. 若用户放弃草稿，可删除对应图片。
5. 删除正式记录时，若图片无其他记录引用，则同步删除图片文件。

### 6.2 存储目录建议

- `Documents/images/medicine/`
- `Documents/images/medical/`
- `Documents/images/drafts/`

### 6.3 图片使用规则

- 页面展示优先读取本地图。
- 识别过程中不上传相册中未被用户选择的图片。
- 不保留额外云端图片副本。

## 7. AI 识别边界

### 7.1 识别任务分类

建议抽象为两个主要识别接口：

```text
recognizeMedicine(images) -> MedicineDraftPayload
recognizeMedicalDocument(images, documentType?) -> MedicalDraftPayload
```

### 7.2 MedicineDraftPayload 建议输出

- 药品名称
- 通用名
- 规格
- 剂型
- 数量
- 单位
- 有效期
- 用途/适应症
- 储存说明
- 低置信字段提示

### 7.3 MedicalDraftPayload 建议输出

- 文档类型
- 就诊日期
- 医院名称
- 科室
- 诊断结果摘要
- 医生姓名
- 处方药列表
- 关键检查指标
- 低置信字段提示

### 7.4 AI 调用边界

- AI 只负责“从图片提取结构化草稿”。
- AI 不负责自动生成医疗建议。
- AI 输出必须可编辑、可删改、可放弃。
- 客户端应记录请求失败原因，但不缓存第三方返回的敏感调试日志。

## 8. 权限与隐私文案

### 8.1 首次使用权限

| 权限 | 使用时机 | 说明 |
| --- | --- | --- |
| 相机 | 拍照录入时 | 拍摄药盒和医院单据 |
| 相册 | 从相册选图时 | 导入已拍摄资料 |
| 通知 | 开启提醒时 | 发送过期和库存提醒 |
| 生物识别 | 首次开启应用保护时 | 保护本地健康资料 |

### 8.2 AI 识别提示文案建议

> 为完成图片识别，所选照片会发送给第三方 AI 服务进行解析。识别完成后，结构化结果和原图只保存在你的本机。当前版本不会将这些数据同步到本应用的服务器。

### 8.3 隐私说明要点

- 应用不提供账号体系，不在自建服务器留存健康数据。
- 删除记录时，会同步删除本地图片文件。
- 若用户依赖系统备份能力，恢复行为由 iPhone 或 Android 的系统备份机制决定。
- 后续若启用多设备同步，需要单独更新隐私说明、账号机制和数据传输策略。

## 9. 研发拆分建议

### 9.1 模块拆分

| 开发模块 | 目标 |
| --- | --- |
| 本地数据层 | 建立实体、关系、增删改查能力 |
| 图片与拍照层 | 完成拍照、选图、压缩、落盘和删除 |
| 识别与草稿层 | 完成 AI 调用、草稿存储、确认转正 |
| 业务展示层 | 完成首页、药品、就诊档案、设置页面 |
| 提醒层 | 完成过期和库存计算、通知调度 |
| 安全层 | 完成应用解锁和敏感操作验证 |

### 9.2 依赖关系

- 本地数据层先于页面开发完成基础模型。
- 图片与拍照层、识别与草稿层可并行推进。
- 提醒层依赖 `MedicineBatch` 数据结构稳定后实现。
- 安全层与设置页可以在核心流程稳定后接入。

## 10. 异常处理

| 场景 | 系统策略 |
| --- | --- |
| AI 请求超时 | 保留草稿和原图，允许稍后重试或手动录入 |
| AI 返回字段缺失 | 标记为待补充草稿，突出显示缺失必填项 |
| 本地写入失败 | 不删除原图，提示存储异常并保留当前草稿 |
| 删除正式记录 | 同步清理无引用图片，并刷新提醒计算 |
| 通知权限关闭 | 首页仍展示提醒，但不发系统通知 |

## 11. 技术验收点

- 正式记录断网重启后仍可完整读取。
- 草稿未确认前不会污染正式列表和提醒结果。
- 删除记录后，本地文件不会残留孤儿图片。
- 药品批次提醒按本地日期正确计算。
- 无网络时用户仍可从拍照流程进入手动录入。
